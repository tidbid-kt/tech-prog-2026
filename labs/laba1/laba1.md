# Лаба 1 – Git

В этой лабораторной работе мы научимся базой работе с системой контроля версий Git.

Git представляет из себя утилиту для командной строки, которая называется `git`.

# Что нужно сделать к защите

1. Создать локальный git репозиторий с пустым файлом `README.md`;
2. Сделать первый коммит в ветку `main`;
3. Добавить удалённый **приватный** репозиторий на хостинге [GitHub](https://github.com) (или любом другом, как вам удобнее);
4. Запушить локальные коммиты в удалённый репозиторий по протоколу **https**;
5. Создать от ветки `main` ветку `hotfix/task1`;
6. Добавить в `README.md` строку, в которой содержится ваше **ФИО и номер группы**;
7. Через командную строку сделать коммит, указав **в качестве сообщения ФИО и номер группы**;
8. Запушить ветку `hotfix/task1` в удаленный репозиторий;
9. Слить изменения, сделанные в ветке `hotfix/task1` в ветку `main`;
10. Запушить ветку `main` в удаленный репозиторий;

К защите нужно иметь репозиторий на (как вариант) [GitHub](https://github.com), в котором будет две ветки: `main` и `hotfix/task1`. 
В ветке`main` должно быть два коммита (самый первый и тот, что был добавлен в рамках `hotfix/task1`).

Замечательно! Теперь в нашем удаленном репозитории есть ветка с нормальным описанием проекта. 
Однако хорошо бы эту ветку иметь локально. Давайте приведем состояния локального и удаленного репозитория в соответствие!

Забрать недостающие ветки из удаленного репозитория можно командой `git fetch`:

![git fetch](./images/19_git_fetch.png)
Забираем ветки с ремоута

Если не указывать `remote` с которого мы хотим забрать изменения (как это сделал я), 
то гит будет по умолчанию использовать `origin` (как удачно что ремоут именно с таким именем мы и добавили!!!).

Замечательно, теперь в нашем локальном репозитории есть ветка с хотфиксом. Встает вопрос, а как в нее попасть?
Для этого есть команда `git checkout`, в качестве аргумента укажем для нее `hotfix/md-content` - ту ветку, на которую хотим переключиться:

![git checkout](./images/20_git_checkout_on_remote.png)
Переключаемся на ветку

Просто невероятно, но мы видим, что теперь наш файл наполнен описанием! Все потому, что мы ушли с ветки `main` 
и находимся на ветке `hotfix/md-content`, в которую и вносили изменения.

Это все, конечно, хорошо, но данное описание нам хотелось бы видеть и в `main` тоже. 

Вместо того чтобы копировать его через CNTRL + C и вставлять через CNTRL + V, давайте поступим хитрее и интегрируем изменения, сделанные в `hotfix/md-content` в ветку `main`.

Для этого нам нужно переключиться обратно в ветку `main` с помощью команды `git checkout` и выполнить команду 
`git merge`, в качестве аргумента для которой укажем `hotfix/md-content` - ветку, изменения из которой мерджим в `main`:

![git merge](./images/21_git_merge_into_main.png)
Сливаем ветки

`git merge` крайне интересная и сложная команда, однако базово нужно понимать следующее: 
при ее выполнении происходит слияние изменений из той ветки, которая указана как аргумент (в нашем случае из `hotfix/md-content`) 
в ту ветку, в которой вы находитесь (узнать ее можно через команду `git status`, в нашем случае это `main`).

Супер, изменения слиты, однако теперь получается, что в нашем локальном репозитории в ветке `main` 
содержимое файла это красивое описание проекта, а в удаленном репозитории - ещё старая версия (ведь мы слили ветки локально и еще не синхронизировали изменения)!!!

Давайте исправляться и пушить изменения в удаленный репозиторий. Это супер просто, выполняем команду `git push` и готово, даже аргументы не нужны:

![git push](./images/22_git_push_merge.png)
Пушим изменения

Указывать аргументы не надо, потому что гит и так понимает, куда надо пушить, 
ведь в самом начале мы прописали связь данной ветки с удаленной (см. пункт про синхронизацию локального и удаленного репозиториев).

Давайте проверять, что все прошло, заходим на GitHub и видим, всё на месте:

![git push aftermath](./images/23_git_merge_result_ui.png)
Отрыв всего

### Стягивание удаленных изменений

Ну, на самом деле предыдущий раздел не был последним, забыли одну важную штуку. Представим, что в ваше отсутствие в ветку `develop` наделали изменений.

Симулировать это можно самим: в веб-интерфейсе переключаемся на `develop` и через кнопку **+** выбираем *Create new file*:

![Создание файла на GitHub](./images/27_create_new_file_menu.png)
Create new file

Задаём имя файла (например `file-from-develop`) и любое содержимое:

![Редактор нового файла](./images/28_create_file_editor.png)
Пишем что-нибудь

Коммитим сразу в `develop`:

![Коммит файла в develop](./images/29_create_file_commit.png)
Коммитим в develop

Этих изменений в нашем локальном проекте ещё нет. Перейдём в ветку `develop` (помним про команду `git checkout`) и выполним `git status`:

![develop status](./images/30_git_status_on_develop.png)
Состояние ветки `develop`

> **_NOTE:_** `git status` может написать, что локальная ветка *up to date* с `origin/develop`, даже если на GitHub уже есть новый коммит.
> Git просто еще не знает, что на remote что-то изменилось, а узнает когда будет сделан `git fetch`. После fetch `status` покажет, что вы отстали.
> `git pull` как раз сам делает fetch и подтягивает изменения в текущую ветку.

Так, чтобы забрать изменения, достаточно ~~простой советской~~ команды `git pull`:

![pull](./images/31_git_pull.png)
Пулл изменений

Замечательно, изменения у нас.
